# ADR-003: Schema and data contract

- Status: Accepted
- Date: 2026-10-04
- Deciders: Insharah (scribe), Zara, Aabia
- Task: G-01 (step 3)
- Inputs: `docs/data_facts.md` (generated by `scripts/regen_data_facts.py`, G-02)
- Related plan items: D-02, D-05, sections 5.3 and 4

## Context

G-02 inspected the frozen V1 files. They differ from the draft schema in plan section 5.3 in several ways: real
column names, an opaque `case_id`, dependency ids stored as list columns on the case table, a mapping table that
is 91% explicit `UNMAPPED` rows, and three AMRFinderPlus database versions present in the same tables.

## Decision

### 1. Data layout (the same on every machine)

- Frozen engine inputs go in `data/raw/`, keeping the original sub-folders: `data/raw/curated_v1/`,
  `data/raw/mapping_v1/`, `data/raw/analysis_v1/`. Contents are gitignored; the folders are tracked.
- The 25 frozen manifest json files go in `data/manifest/frozen_v1/` and are **committed** (small, hash-bearing).
- `data/manifest/sha256.txt` (from `scripts/data-hash.ps1 -Mode generate`) is committed. Everyone runs
  `-Mode verify` after copying files.
- Old-pipeline intermediates (`real_isolates_raw`, `synthetic_isolates_raw`, `cases_v1`, `manifest_v1`,
  `real_extraction_manifest`) are **not** copied.
- The superseded `m11_v1/` summaries may be copied for reference, but nothing reads them. `m11_v1_1/` replaces
  them (it fixes a serialisation bug in the determinant lists).

### 2. Column names: keep the frozen names in the database

Keep `target_acc`, `source_snapshot_id`, `standard`, `determinant_identity`, `candidate_antibiotic`,
`relationship`, `rule_status`, `panel_id`. The draft names (`isolate_target_acc`, `snapshot_id`,
`testing_standard`, `determinant`, `antibiotic`, `relation`, `status`, `panel_version`) are retired.
The only rename: every table's `checksum` column becomes `source_checksum` (the name collides across tables and
would be mistaken for a key).
Six isolate columns are lowercased (IFSAC_category, LibraryLayout, Platform, Run, PFGE_PrimaryEnzyme_pattern, PFGE_SecondaryEnzyme_pattern) and new is loaded as new_flag.

### 3. Tables loaded from the frozen files (immutable after load)

### 4. R1 release (first ledger release, as-reported mode)

- `case_state` rows for release `R1` come from the same file. `case_state` (frozen) becomes `state_code`;
  `unresolved_reason` becomes `uncertainty_reason`. Add `phenotype_state` and `genotype_state` columns (the
  evaluator's two stages, ADR-004). `phenotype_values`, `determinants_evaluated` and `determinants_supporting`
  go into `explanation` (JSONB) for display. The frozen `case_state_id` is kept as `source_state_id`.
- `refgene_db_version` is **per case** (`2026-03-24.1` 40,402 cases, `2026-05-15.1` 767, `2026-08-07.1` 689),
  so it is stored on the case state and not only in the release version vector.

### 5. Dependency edges: explode the five id lists

| Frozen list column | Rows after explode | `edge_type` | `dep_type` | `node_type` |
|---|---|---|---|---|
| `ast_evidence_ids` | 41,880 | `derived_from` | `input_evidence` | `ast_evidence` |
| `genotype_evidence_ids_evaluated` | 469,755 | `derived_from` | `input_evidence` | `genotype_evidence` |
| `genotype_evidence_ids_supporting` | 26,972 | `derived_from` | `positive_support` | `genotype_evidence` |
| `mapping_rule_ids_evaluated` | 344,526 | `evaluated_against` | `applicability` | `mapping_rule` |
| `mapping_rule_ids_supporting` | 20,009 | `derived_from` | `positive_support` | `mapping_rule` |

That is **903,142** rows. `determinants_evaluated` and `determinants_supporting` are not exploded (they repeat
the mapping lists by name; counts 344,526 and 20,009 match). Add seven version edges per case
(`refgene_db_version`, `amrfinderplus_version`, `mapping_version`, `case_rule_version`,
`curation_rule_version`, `panel_id`, `source_snapshot_id`; 41,858 x 7 = 293,006) with `dep_type =
provenance_version`. Total about **1.2 million** edges, the low end of the proposal's 1 to 5 million
estimate. The taxonomy in plan section 3.1 gains one type, `input_evidence`: an item the evaluator consumed
whether or not it supported the state.

### 6. Applicability is keyed on the pair, not on the rule id

`mapping_rule` ids embed the AMRFinderPlus database version (three versions, 14,512 rows each). A new version
produces new ids for the same determinant and drug, so no existing edge points at them. The `applicability`
table is therefore keyed on `(determinant_identity, candidate_antibiotic)`, derived by joining
`mapping_rule_ids_evaluated` to `mapping_rule`. Impact selection for a new or changed mapping queries this pair.

### 7. Engine tables

Unchanged from plan section 5.3 (`version_node`, `interpretation_rule`, `release`, `case_state`, `dependency`,
`applicability`, `change_event`, `reeval_run`, `review_event`, append-only triggers), apart from the
additions above. Section 5.3's source-table DDL is superseded by this ADR.
Release gains release_seq and its lifecycle guards (migration 0004, I-02)

### 8. Toolchain

- Python 3.12 in a project venv (not conda base). `pandas==3.0.5`, `pyarrow==25.0.1` pinned. Docker image
  `python:3.12-slim`. PostgreSQL 16.
- Migrations are plain numbered SQL files in `db/migrations/` (`0001_*.sql`), applied by a small runner. No ORM
  for schema management. SQLAlchemy Core is allowed for queries (OD-7 default).

## Consequences

- One adapter in `ingest/` maps frozen names to the engine's neutral types (ADR-001, ADR-004).
- The case table already holds the realised dependency edges, so A-03 mostly explodes and types them. A-02 can
  also compare the evaluator's own dependency lists against these.
- Loading `genotype_evidence` and the edge table is the heaviest load, around 0.9 million edge rows plus 413,116
  evidence rows. It is a one-off bulk `COPY`.
- The defaults in `scripts/regen_data_facts.py` (`--data-dir`, `--manifests-dir`, the exclude pattern) must move
  to the new layout (follow-up F-1).

## Amendment 1 (2026-10-05)

Raised and written by Aabia (A-01, PR #61). Closes OP-1 and OP-3.

1. **OP-1 is closed, confirmed with one clarification.** Source: the legacy implementation `scripts/build_case_states_v1.py`. The spec itself only speaks of ids "used"; the split into two lists comes from the implementation.
   - `*_evaluated` is every genotype evidence row of the isolate's authoritative representation, paired with the mapping rule consulted for that antibiotic. Rules that map to nothing (`UNMAPPED`) are included.
   - `*_supporting` is the subset of items that decided the genotype state. For a decisive state these are the decisive items. For a contextual state these are the contextual items, so the lists are not limited to resistance support. The counts agree: 7,472 decisive plus 3,534 contextual cases equals the 11,006 cases with a non-empty supporting list.
   - The edge mapping in section 5 stands. Read `positive_support` on the two supporting lists as "evidence that decided the state", which includes contextual evidence.
2. **OP-3 is closed.** The spec is in the repository as `docs/spec/CASE_RULES_V1.md`, renamed from `M8_2_CASE_RULES_V1.md` to match its rule ID. Its sha256 is `c4338fc4c50fdadb2c62a92c7bf3c8c3100d467b2d3aaa7a9a00c8ba573406f2`, as recorded above. The file is marked `-text` in `.gitattributes` so the hash is the same on every machine. Provenance is in `docs/spec/README.md`.
